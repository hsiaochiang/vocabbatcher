# WORKFLOW.md — 兩層 Vibe Coding 執行規範

> 本檔是「人 + 兩個 AI」協作流程的總綱。
> 對象：負責人(懂系統分析、不寫程式)。
> 配套文件：行為規範看 `AGENTS.md`、進度看 `PROGRESS.md`、決策看 `DECISIONS.md`。
>
> **本專案背景：** VocabBatcher 原本由 OpenSpec + GitHub Copilot（WOS agent）驅動，
> 文件在 `docs/roadmap.md`、`docs/decision-log.md`、`.github/copilot-instructions.md` 等處。
> 2026-07-06 起負責人決定逐步改用本套流程，兩套系統過渡期並存，見 `DECISIONS.md`。

## 0. 一頁速覽(只看這段也能上手)

```
        ┌─────────────────────┐   交接合約    ┌──────────────────┐
  負責人 │  規劃層 (Planner)    │ ───────────> │  執行層           │
 ◄────► │  想清楚 + 拆切片     │    BRIEF      │  照 brief 寫程式  │
        └─────────────────────┘   <───────── └──────────────────┘
              產出/維護文件          PROGRESS      開工讀 / 收工寫
                                    DECISIONS      (執行層自動化)
```

- **兩個角色**：規劃層 = 規劃與決策；執行層 = 寫程式。中間只有一個交接點。
- **交接靠文件，不靠對話**：規劃層規劃完，寫成一份 `BRIEF`，執行層只看這份就能做對。
- **記憶靠 PROGRESS.md**：兩邊每次開工先讀它、執行層收工必更新它。
- **變動靠 DECISIONS.md**：任何偏離原始需求的改動，當下記一筆。
- **關卡制**：五階段，每階段負責人驗收過才往下；做一塊驗一塊，不一口氣做完。

## 1. 為什麼是兩層(設計理由)

### 1.1 不可省的是「規劃 / 執行」二分，不是層數，也不是特定工具

多代理開發的核心證據指出：把「規劃」和「執行」放在同一個 AI 會發生 **context pollution** —— 執行時堆積的 debug 雜訊，會污染規劃判斷，讓決策變差。所以真正必要的是把這兩件事分到不同 session：

- **規劃層 (planner)**：跟負責人來回討論需求、定 roadmap、拆切片、做決策。context 乾淨，專注思考。
- **執行層 (implementer)**：只在 repo 裡照 brief 寫程式。context 可以堆滿 log，不影響上游。

### 1.2 為什麼是兩層而非三層

兩層 = 一個交接點。每多一次 AI 之間的交接，context 就多一次斷裂風險。把「拆切片」併進規劃層後：

1. **瓶頸在規劃品質，不在打字速度。**
2. **執行層是已驗證的寫程式層，不能砍。**
3. **少一個交接點 = 少一個失真點。**

### 1.3 兩層化的關鍵負擔轉移(重要)

規劃層一肩扛起「拆切片 + 顧跨切片一致性」。若某階段切片很多、彼此相依複雜，規劃層的 `STAGE_N_PLAN.md` 必須把相依順序寫清楚，否則執行層會因為看不到全局而把切片做歪。**這是兩層流程的單一最大變數。**

## 2. 文件體系(誰產出、誰讀、何時更新)

### 2.1 過程文件(貫穿開發)

| 文件 | 角色定位 | 產出層 | 讀取層 | 更新時機 |
|---|---|---|---|---|
| `AGENTS.md` | 兩層共同憲法(行為規範) | 規劃層 | 全部(執行層自動讀) | 規則或架構改變時 |
| `REQUIREMENTS.md` | 原始需求基準線(spec) | 規劃層，負責人簽核 | 全部 | 需求變更時(同步留痕 DECISIONS) |
| `ROADMAP.md` | 全案藍圖：階段切分 + 順序 | 規劃層 | 全部 | 階段切分定案 / 重大調整時 |
| `STAGE_N_PLAN.md` | 單一階段的切片拆分 + 相依順序 | 規劃層 | 規劃層自用 → 生成 BRIEF | 進入某階段時 |
| `BRIEF_SliceN.md` | 單一切片的施工規格(tasks) | 規劃層 | 執行層 | 開一個切片時 |
| `PROGRESS.md` | 一頁進度儀表板(Memory Bank) | 執行層(主) | 全部，**開工先讀** | **每個 session 收工必更新** |
| `DECISIONS.md` | 變更與決策日誌(ADR) | 發生偏離的那層 | 全部 | 任何偏離需求的當下 |

## 4. 五階段關卡流程(雙軌驗收法 v2)

| 階段 | 規劃層做什麼 | 執行層做什麼 | Exit Gate(負責人驗收) |
|---|---|---|---|
| ① 系統分析 | 逼問需求、寫 `REQUIREMENTS.md`、開 `PROGRESS.md`、定 `ROADMAP.md` | — | 需求清單確認、範圍凍結 |
| ②a 設計 + UX | 規劃畫面，標出對應功能 | 做可點擊靜態雛形(假資料) | 點過雛形、UX 檢核過才寫後端 |
| ③ 開發(垂直切片) | 寫 `STAGE_PLAN` + 逐切片 `BRIEF` | 照 brief 一次做一片，做完停下 | **親自操作該切片**確認才做下一片 |
| ④ 測試 + 漂移管控 | 整理 R 對照驗收表 | 執行測試、修 bug | 在乎的功能全測過、偏離都記錄 |
| ⑤ 交付上線 | 寫 `USER_MANUAL` / `DEVELOPER_LOG` | UI 截圖自查、上線檢查表 | 截圖確認、乾淨環境走過、檢查表全勾、兩份成果文件交付閘已過 |

**本專案目前在 ④ 測試 + 漂移管控。**

## 5. 自動化機制(執行層)

兩層流程的文件紀律，理想上靠**執行層的三個自動化動作**強制執行，不靠 AI 自律。
**本專案尚未鋪設 `.codex/hooks.json`**，暫時改靠 §5.3 的等價做法。

### 5.1 三個自動化動作各自做什麼

| 動作 | 觸發時機 | 效果 |
|---|---|---|
| **SessionStart** | 新建/恢復對話 | 自動讀 `PROGRESS.md`，把專案脈絡塞進模型。 |
| **PostToolUse** | 實際改檔時 | 改動程式 / 需求檔後，提醒檢查是否需要記 `DECISIONS.md`。 |
| **Stop** | 每次收工 | 檢查 `PROGRESS.md` 今天有沒有更新；沒更新就擋下，要求補。 |

### 5.2 Codex CLI 實作方式(若日後鋪設)

- 定義檔：`.codex/hooks.json`(隨專案進 Git)。
- 腳本：`.codex/hooks/` 內雙平台。
- 信任要求：專案必須被 Codex CLI 信任；新增或修改 hook 後要重新信任。

### 5.3 目前替代做法(尚未鋪 hook 時)

> 把這三件事寫進每份 `BRIEF` 的開場與收尾指令：
> (1) 開場：先讀 `PROGRESS.md`；(2) 收工：更新 `PROGRESS.md`；(3) 改動需求/程式：檢查 `DECISIONS.md`。
> 效果等價 —— 自動化的目的只是「不靠自律」，用哪種機制達成不重要。

## 6. 規劃層的紀律(skill `planner-sop`，取代 hook)

**每次開工(SOP)：**
1. 先讀 `PROGRESS.md` 恢復脈絡。
2. 確認現在在五階段的哪一關、下一步是什麼。
3. 若要進新階段 → 先寫 `STAGE_N_PLAN.md`；若要開切片 → 先寫 `BRIEF`。

**每次收工(SOP)：**
1. 若有需求 / 範圍變動 → 更新 `REQUIREMENTS.md` 並在 `DECISIONS.md` 留痕。
2. 若規則 / 架構變動 → 更新 `AGENTS.md`。
3. 明確問負責人：「這一關過了嗎？可以往下嗎？」

## 7. 一個切片的完整生命週期

```
1. 規劃層開工 → 讀 PROGRESS.md，確認在哪個階段、要做切片 N
2. 規劃層寫 STAGE_N_PLAN.md(若該階段尚未拆切片)→ 排好切片相依順序
3. 規劃層寫 BRIEF_SliceN.md → 這是交給執行層的合約
4. 負責人看 brief，確認方向(可選的輕量確認)
5. 執行層開工 → 讀 PROGRESS.md
6. 執行層照 brief 寫程式；若偏離需求 → 記 DECISIONS.md
7. 執行層做完該切片 → 更新 PROGRESS.md(切片狀態 + 下一步)
8. 執行層收工 → 確認 PROGRESS 已更新
9. 執行層給負責人：「現在你能做什麼」+ 操作步驟 + 關鍵截圖
10. 負責人親自操作驗收 → 過了才回到步驟 1 做下一切片
```
