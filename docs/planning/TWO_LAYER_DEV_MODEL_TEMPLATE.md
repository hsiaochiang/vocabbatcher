# 兩層 Vibe Coding 開發模型 — 可移植範本

> 這份文件從 VocabBatcher 專案（2026-02 ~ 2026-08）的實際運作中萃取出來，
> 是「非工程背景負責人 + 兩個 AI（規劃層／執行層）」協作模式的可移植版本。
> **要用在新專案時：整份複製到新專案根目錄，改名成 `AGENTS.md`，
> 把方括號 `[...]` 的地方填成新專案的實際內容，其餘結構原則上不用大改。**
> 本檔本身不用留在新專案裡（它是給你抄的範本，不是給 AI 讀的規範檔）。

---

## 這個模型解決什麼問題

如果你（負責人）懂系統分析、會做決策，但不寫程式，又想用 AI 開發一個完整專案，會遇到兩個核心問題：

1. **一個 AI 又規劃又寫程式，會把自己搞亂**——執行時堆積的 debug 雜訊、反覆嘗試的錯誤路徑，會污染規劃判斷，讓後續決策變差（context pollution）。
2. **沒有文件當作記憶，AI 每次開新對話都要重新理解專案**，你要一直重複解釋背景，AI 也容易做出跟之前決策矛盾的事。

**解法：把「規劃」跟「執行」分成兩個角色，中間只留一個交接點（BRIEF 檔案），並用一組固定文件當作跨 session 的共同記憶。**

---

## 核心角色

| 角色 | 職責 | 不做的事 |
|---|---|---|
| **規劃層（Planner）** | 跟負責人討論需求、拆切片、寫 BRIEF、做決策、追根因、驗收前抽查程式碼品質 | 不直接寫程式（除非是文件、設定檔這類低風險、規劃層本來就該碰的東西） |
| **執行層（Implementer）** | 只在 repo 裡照 BRIEF 寫程式，收工回報 | 不自己決定範圍、不跳過 BRIEF 邊界、不猜測式亂改跟本次任務無關的程式碼 |

### 角色綁定對照（換工具時只改這一行）

| 抽象角色 | 目前綁定 | 備註 |
|---|---|---|
| 規劃層 (Planner) | `[填：例如 Claude Code / Cowork]` | |
| 執行層 (Implementer) | `[填：例如 Codex CLI / 其他 agentic coding CLI]` | |

換工具（例如執行層從 Codex CLI 換成別的 CLI）時，只需要改這張表，其餘流程不變——這是「角色」跟「工具」分離設計的重點。

---

## 為什麼是兩層，不是三層或一層

- **一層**：規劃跟執行混在同一個對話，前面提過的 context pollution 問題。
- **三層以上**：每多一次 AI 之間的交接，就多一次資訊失真的風險；瓶頸通常在「規劃品質」不在「打字速度」，加更多層不會讓規劃變好。
- **兩層**：一個交接點（BRIEF），最少的失真風險，同時解決 context 污染問題。

兩層化之後，規劃層要一肩扛起「拆切片＋顧跨切片一致性」——如果某階段切片很多、彼此相依複雜，規劃層必須在 `STAGE_N_PLAN.md` 把相依順序寫清楚，否則執行層看不到全局會做歪。**這是這個模型單一最大的變數，值得規劃層特別謹慎。**

---

## 文件體系

| 文件 | 作用 | 產出層 | 何時更新 |
|---|---|---|---|
| `AGENTS.md` | 兩層共同的行為規範（就是這份範本填完的樣子） | 規劃層 | 規則或架構改變時 |
| `REQUIREMENTS.md` | 原始需求基準線，負責人簽核 | 規劃層 | 需求變更時（同步記 `DECISIONS.md`） |
| `ROADMAP.md` | 全案藍圖：階段切分與順序 | 規劃層 | 階段切分定案／重大調整時 |
| `STAGE_N_PLAN.md` | 單一階段的切片拆分＋相依順序 | 規劃層 | 進入某階段時 |
| `PROGRESS.md` | **一頁進度儀表板，跨 session 記憶** | 兩層共同維護 | **每次收工必更新** |
| `DECISIONS.md` | 變更與決策日誌 | 發生偏離的那層 | 任何偏離原始需求的當下 |

### 單一切片的三份成對檔案（這個模型最實用的細節）

每次要執行層做一個切片，規劃層產出**三份檔案**，不是一份：

1. **`BRIEF_<切片名>.md`** — 完整施工規格：背景、目標、現況（可重用什麼）、任務清單、邊界（明確列出「這次不做什麼」「不要動什麼」）、驗收標準（負責人白話操作步驟）、收工指令。
2. **`<執行工具>_PROMPT_<切片名>.md`** — 可以直接複製貼上餵給執行層 CLI 的包裝提示詞，內容是「讀 AGENTS.md → 讀這份 BRIEF → 照做 → 收工前寫報告」，**最後一定要求執行層把結果寫成第三份檔案**，不要讓執行層只在終端機印出一大段文字要負責人自己複製貼給規劃層。
3. **`REPORT_<切片名>.md`**（執行層產出）— 結構化收工報告：改了什麼、是否偏離 BRIEF、測試/建置結果、給負責人的白話驗收步驟、卡住的地方。**規劃層直接讀這份檔案，不需要負責人手動貼終端機輸出**，大幅減少往返成本。

這個三檔案模式解決了一個很實際的問題：負責人不是工程師，沒辦法、也不該負責在規劃層與執行層之間手動搬運技術性的終端機輸出。**BRIEF 給規格，PROMPT 是可執行的信封，REPORT 是回條**——三者分離讓每個角色只需要讀自己看得懂、用得到的那份。

## 五階段關卡（雙軌驗收法）

| 階段 | 規劃層做什麼 | 執行層做什麼 | Exit Gate（負責人驗收） |
|---|---|---|---|
| ① 系統分析 | 逼問需求、寫 `REQUIREMENTS.md`、開 `PROGRESS.md`、定 `ROADMAP.md` | — | 需求清單確認、範圍凍結 |
| ②a 設計＋UX | 規劃畫面，標出對應功能 | 做可點擊靜態雛形（假資料） | 點過雛形、UX 檢核過才寫後端 |
| ③ 開發（垂直切片） | 寫 `STAGE_N_PLAN.md`＋逐切片 `BRIEF` | 照 BRIEF 一次做一片，做完停下 | **親自操作該切片**確認才做下一片 |
| ④ 測試＋漂移管控 | 整理需求對照驗收表 | 執行測試、修 bug | 在乎的功動全測過、偏離都記錄 |
| ⑤ 交付上線 | 寫 `USER_MANUAL.md`／`DEVELOPER_LOG.md` | UI 截圖自查、上線檢查表 | 檢查表全勾、成果文件交付閘已過 |

**嚴禁一口氣做完才給看**——垂直切片，每片做完停下來等負責人確認，過了才做下一片。

## 從實戰中學到、值得直接抄的規則

這些是 VocabBatcher 專案實際運作八個月後才浮現的教訓，直接寫進範本，省得新專案重踩一次：

### 1. 執行層連續猜錯根因時，規劃層要親自下場驗證，不要再發一輪猜測式 BRIEF

VocabBatcher 有一個登入問題，執行層依序猜了「跨網域儲存限制」「換部署平台」兩輪都沒修好。規劃層後來直接用瀏覽器自動化工具重現問題、讀 console 錯誤訊息，才在幾分鐘內找到真正根因（兩個疊加的架構衝突）。

**規則：同一個問題如果執行層已經猜了兩輪還沒修好，規劃層應該考慮親自用工具（瀏覽器自動化、`curl`、直接讀設定檔／log）驗證事實，而不是繼續發第三份「換個方向猜猜看」的 BRIEF。** 猜測式除錯的往返成本，通常遠高於規劃層花十分鐘自己動手查。

### 2. UI/UX 類的修正，要求執行層收工前自己跑一輪自動化驗證

純視覺／互動類的修正（不涉及需要真實帳號登入等外部依賴的流程），要求執行層在收工前用瀏覽器自動化工具（例如 Playwright）自己跑一輪基本驗證——開頁、截圖、點關鍵路徑、檢查畫面元素——把能自動驗證的部分先驗過，減少負責人手動測試才發現問題的往返次數。這個規則實際發揮效果：VocabBatcher 有一輪修正就是靠執行層自己的 Playwright 測試，在收工前抓到並修好一個「單字庫還沒載入完成就開考試頁會出錯」的問題。

**不是要求建立完整的長期 CI/E2E 測試框架**——那是更大的工程決策，需要另外討論。這裡只是「執行層自我驗證」的輕量工具，跑完的腳本留著即可，不用刻意整合進 CI。

### 3. 一開始就準備好一鍵部署腳本

不管是 `deploy.ps1`、`deploy.sh` 或其他形式，把部署步驟（build＋deploy）包成一個腳本，放在專案根目錄。每次要負責人手動打兩三行指令，就是兩三次可能打錯或漏做的機會。

### 4. BRIEF 的「邊界」章節要明確列出「不要動什麼」

尤其是專案裡有過慘痛教訓、好不容易修好的東西（例如某個路由函式庫選型、某段安全規則），每次開新的 BRIEF 都要明確提醒執行層「這些已經驗證過，不要因為這次任務動到」。不要假設執行層會自己知道要避開——它只看得到這一份 BRIEF，看不到你們過去踩過的坑，除非你寫進去。

### 5. 資料正確性問題可能藏在功能表面之下，肉眼核對比程式碼審查更快抓到

VocabBatcher 有一個「頁碼跟課本印刷頁碼對不上」的資料錯誤，程式碼邏輯完全正確（篩選、出題都照著資料跑），但資料本身的語意是錯的，這種錯誤用程式碼審查幾乎抓不到，是負責人拿實體參考資料肉眼核對才發現的。**功能涉及外部真實世界的資料（頁碼、日期、地址、單位換算……）時，安排負責人用真實情境肉眼核對一次，不要只信任程式碼邏輯正確 = 結果正確。**

### 6. 每次要開新 session 接續開發，先準備一份「下一步啟動提示詞」

長期專案跨多個對話 session 開發時，寫一份 `NEXT_SESSION_PROMPT_<階段>.md`，內容包含：要先讀哪些文件恢復脈絡、現況摘要、已知地雷（哪些東西絕對不要動）、這次 session 要做的具體任務。負責人開新 session 時直接貼上這份提示詞，不用每次重新口述背景。

## 新專案設定清單

在新專案要套用這個模型時，依序做：

- [ ] 複製本檔，改名 `AGENTS.md`，填完「角色綁定對照」表與專案技術要點。
- [ ] 跟負責人逼問需求，產出 `REQUIREMENTS.md`（白話功能清單＋「先不做」清單）。
- [ ] 建立 `PROGRESS.md` 初版。
- [ ] 定 `ROADMAP.md`（階段切分＋順序）。
- [ ] 建立空的 `DECISIONS.md`（放好格式範本即可，等第一次偏離發生時再寫）。
- [ ] 準備一鍵部署腳本（若專案有部署需求）。
- [ ] 進入第一個階段時，寫第一份 `STAGE_1_PLAN.md`，開始第一片 `BRIEF`。

---

## DECISIONS.md 記錄格式

```
## [日期] 決策標題
- 狀態：已採納 / 已否決 / 待確認
- 背景：為什麼要改（測試發現什麼／bug／新限制）
- 改動：具體改了什麼
- 影響的原始需求：REQUIREMENTS.md 第 X 條（原本…→ 現在…）
- 負責人是否同意：是 / 否 / 待確認
```

狀態為「待確認」時，AI 不可逕自實作，必須先得到負責人同意。
