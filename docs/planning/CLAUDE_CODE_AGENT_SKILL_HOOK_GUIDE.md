# Claude Code 工具層設定指南 — Agent / Subagent / Skill / Hook 可移植範本

> 這份文件是 `TWO_LAYER_DEV_MODEL_TEMPLATE.md` 的配套文件。那份講的是「規劃層／執行層」的協作方法論；
> 這份講的是**規劃層自己（Claude Code）**可以怎麼用內建工具（fork、Skill、Hook）把方法論裡的重複動作自動化。
> 兩份文件分開，是因為方法論可以套用在任何 AI 工具組合上，但這份文件的內容專屬於 Claude Code 這個工具本身的能力。
> **要用在新專案時：整份複製到新專案，把方括號 `[...]` 填成新專案的實際內容。**

---

## 這份文件從哪裡來

VocabBatcher 專案跑完 M1~M3 加一輪 UI/UX 修正後回顧，發現規劃層（Claude Code）自己有三個地方，明明有現成工具可以自動化，卻整個 session 都在手動做：

1. 用瀏覽器工具反覆除錯時，把大量雜訊留在主對話裡，應該要 fork 出去。
2. 十幾次手動重寫「BRIEF + 執行層提示詞」這組固定格式的檔案，應該要做成 Skill。
3. 「開工先讀進度檔、收工要更新進度檔」這條規則完全靠自律，應該要掛 Hook 強制檢查。

這份文件把這三個教訓整理成可以直接套用的規則跟範本。

---

## 1. 什麼時候該 fork 自己（subagent）

### 判斷標準

**不是看任務大小，是看「這次工具呼叫產生的雜訊，未來還需不需要」。** 如果需要反覆試錯、多輪讀取工具輸出才能得到一個結論（除錯、調查、多輪嘗試），而你真正在意的只有「最後的結論」，這種情況應該 fork 出去做，只把結論帶回主線程。

### 具體訊號（符合任一個就該考慮 fork）

- 要連續呼叫瀏覽器自動化工具（截圖、讀 console、讀 network requests）超過 2-3 輪去追一個問題。
- 要讀一堆 log、跑一堆 `curl`/`grep` 去定位一個根因，中間會有很多「試了發現不是這個、再試下一個」的過程。
- 要做一次性的稽核／盤點（例如把一整個 codebase 的檔案讀過一輪找問題），輸出是一份報告，過程中的檔案內容不需要留在主線程。

### 具體訊號（不需要 fork）

- 單次、目標明確的檔案讀取或編輯。
- 需要跟負責人即時互動確認的決策（fork 是背景執行，中途不能問問題）。
- 工作量雖大但每一步都是「做完就對」，不涉及反覆試錯（例如照著清單改十個檔案的同一種修正）。

### 這個教訓的實際案例

VocabBatcher 有一個登入問題，規劃層直接在主對話裡用瀏覽器工具做了好幾輪「導航→截圖→讀 console→讀 network」的除錯循環才找到根因。這些工具呼叫的輸出雖然使用者看不到，但持續留在規劃層的 context 裡，會擠壓後續判斷的品質——這正是 fork 存在的理由：**把雜訊留在 fork 裡，只把「真正根因是什麼」這個結論帶回來。**

## 2. 什麼時候該做成 Skill

### 判斷標準

如果你發現自己在**同一個專案裡，用幾乎一模一樣的結構重複做同一件事三次以上**，這就是訊號——把它固定成 Skill，之後不用每次重新組織格式，也不會因為累了漏掉某個章節。

### 這個模式最適合套用的兩種情境

無論用什麼協作方法論，長期專案幾乎都會反覆出現這兩種動作：

**A. 「開工作項」**：把一個需求拆解成一份完整規格（背景、目標、任務、邊界、驗收標準），交給某個執行角色（可能是另一個 AI 工具、可能是人類團隊成員）。

**B. 「收工作項」**：對方回報完成後，核對回報內容是否屬實、更新進度追蹤文件、視情況補記決策日誌，再給需求方一份消化過的驗收摘要。

VocabBatcher 專案把這兩個動作做成 `open-brief` / `close-brief` 兩個 Skill（見 `.claude/skills/open-brief/SKILL.md`、`.claude/skills/close-brief/SKILL.md`，可以直接複製過去改專案特定內容當範本）。核心設計原則：

- **`open-brief` 類的 Skill**：開工前要求先讀進度追蹤文件恢復脈絡、讀決策日誌找「不要再犯」的地雷、找 1~2 份最近的範例維持格式一致；產出的規格書要固定包含「邊界」章節，把已知地雷明確點出來（不要假設執行方會自己知道要避開）。
- **`close-brief` 類的 Skill**：**不要照單全收回報內容**——用版本控制工具（`git diff`/`git status`）核對回報跟實際改動是否一致，這是整個 Skill 存在的意義（多一層查核）；更新進度文件跟決策日誌；給需求方的驗收摘要要消化過，不要整份原始回報照貼。

### 什麼情況不需要做成 Skill

- 只發生過一兩次、看起來不會再重複的任務。
- 高度依賴人類主觀判斷、沒有固定產出格式的工作（例如純粹的創意發想討論）。

## 3. 什麼時候該掛 Hook

### 判斷標準

當某條規則**完全靠自律維持**（寫在文件裡提醒自己「開工要做 X、收工要做 Y」），但實際執行時常常忘記或跳過——這種情況該用 Hook 把它變成自動觸發，而不是繼續加強措辭提醒自己。**Hook 解決的是「不靠自律」的問題，跟提醒的內容本身無關。**

### 具體訊號

- 文件裡出現「每次開工先讀 X」「每次收工記得更新 Y」這種句子，但沒有任何機制強制檢查有沒有真的做到。
- 想要「如果忘記做某件事，系統自動提醒」而不是「靠自己記得」。

### 這個教訓的實際案例：收工檢查進度文件有沒有更新

VocabBatcher 掛了一個 `Stop` hook（每次 Claude Code 收工觸發），檢查專案的進度追蹤文件（`PROGRESS.md`）在這個 session 裡有沒有被修改過，沒有的話印出提醒（**只提醒，不阻擋**，因為不是每個 session 都一定有進度變動要記錄，例如純討論的 session）。

實作方式（`.claude/settings.json`，跟著專案進 git；標記檔本身要加進 `.gitignore`，因為那是每個 session 的暫時狀態，不是需要版控的內容）：

```json
{
  "hooks": {
    "SessionStart": [
      {
        "hooks": [
          {
            "type": "command",
            "shell": "bash",
            "command": "mkdir -p .claude && date +%s > .claude/[你的標記檔名稱，例如 .progress-session-marker]"
          }
        ]
      }
    ],
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "shell": "bash",
            "command": "marker=.claude/[標記檔名稱]; file=[你的進度追蹤文件，例如 PROGRESS.md]; if [ ! -f \"$marker\" ]; then printf '{}'; elif [ \"$file\" -nt \"$marker\" ]; then printf '{}'; else printf '{\"systemMessage\": \"⚠️ [你的進度文件檔名] 尚未更新，請確認這個 session 是否需要補上工作紀錄\"}'; fi"
          }
        ]
      }
    ]
  }
}
```

原理：`SessionStart` 在對話一開始記一個時間戳記檔案；`Stop` 每次收工比對「進度文件的修改時間」跟「這個時間戳記」誰比較新——進度文件比較新就代表這個 session 裡有更新過，安靜結束；沒有的話印出 `systemMessage` 提醒（`systemMessage` 只是顯示訊息，不會擋下收工動作）。

**設定完要注意**：新增或修改 `.claude/settings.json` 不會被當下正在跑的 session 自動偵測到（設定監看器只認得 session 開始時就存在的檔案），要跑一次 `/hooks`（重新讀取設定）或重開 session 才會生效。

### 其他值得考慮的 Hook 時機（沒有在 VocabBatcher 用到，但符合同一個判斷標準）

- `PostToolUse` 搭配 `Write|Edit` matcher：改完程式碼自動跑格式化工具或 linter。
- `SessionStart`：自動把進度文件的內容印出來，取代每次要負責人手動貼「下一步啟動提示詞」。
- `PreToolUse` 搭配 `Bash` matcher：對高風險指令（例如 `git push --force`）加一層額外確認。
