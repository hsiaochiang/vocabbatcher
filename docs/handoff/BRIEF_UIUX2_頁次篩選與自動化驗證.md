## 目標（一句話）
> 建立批次時，使用者能先選「頁次範圍」快速挑出這個範圍內的單字（比對照實體課本的實際使用習慣），原有的頻率/詞性/搜尋篩選改為次要選項；本片的修正結果由執行層自己用 Playwright 先驗證過一輪。

## 任務

### 1. 批次建立器改成「頁次」為主要挑選方式
- **檔案：** `src/pages/BatchBuilderPage.tsx`
- **現況：** 目前篩選只有「頻率」「詞性」「搜尋文字」三種 chip/輸入，完全沒有頁次篩選；使用者要照課本頁數選字目前做不到。
- **修法：**
  - 新增頁次範圍篩選（最小頁～最大頁），仿照 `ExamSetupPage.tsx` 已有的頁數輸入 UI 風格（兩個數字輸入框＋「至」）與 `src/services/exam.ts` 的 `getPageRange(allWords)` 取得全書頁數上下限當預設值。
  - 篩選邏輯：單字的 `source_page: number[]` 只要有任一頁落在使用者設定的範圍內，就算符合（比照 `exam.ts` 裡 `generateExam` 篩選候選池的寫法：`w.source_page.some((p) => p >= minPage && p <= maxPage)`，可以直接重用或抽成共用函式）。
  - **版面調整**：頁次範圍篩選放在畫面最上面、視覺上最主要的位置（例如篩選區塊的第一排）；原有的頻率、詞性篩選降為次要位置（可以維持原本的 chip 樣式，但排在頁次篩選下方，或做成可收合的「進階篩選」，你評估實作量後決定，不用做得太複雜）；搜尋文字輸入框保留在容易找到的位置（很多使用者會直接找特定單字）。
  - 預設狀態：進入頁面時頁次範圍預設是全書範圍（不篩選），使用者可以縮小範圍；不要求使用者每次都要先選頁次才能看到單字列表。
  - 「顯示 N 筆」的計數要包含頁次篩選後的結果。

### 2. 建立 Playwright 自動化驗證
- **安裝依賴**：在 `exam-vocab-batcher/` 加入 `@playwright/test` 作為 devDependency（`npm install -D @playwright/test`，並執行一次瀏覽器安裝指令，例如 `npx playwright install chromium` 這種只裝 Chromium 就好、不用裝全部瀏覽器，加快速度）。
- **驗證範圍**：針對**不需要真實 Google 帳號登入**的頁面與流程做自動化檢查，例如：
  - 首頁載入後，能看到符合「沒有批次時主 CTA 是建立新批次／已有批次時主 CTA 是開始考試」的邏輯（可以用 localStorage 預先塞資料模擬「已有批次」情境，或至少驗證「沒有批次」情境）。
  - 批次建立器：驗證頁次範圍輸入後，單字列表確實有依範圍篩選變化（例如設定一個很窄的頁次範圍，確認顯示的筆數變少）。
  - 翻牌卡、考試設定頁、考試作答頁的基本渲染與可點擊互動（不涉及登入的部分）。
  - 用 Playwright 的 `expect(page).toHaveScreenshot()` 或至少截圖存檔的方式留存視覺證據（截圖檔案不用強制比對基準線，這次只是輔助驗證用，不用建完整的視覺回歸測試框架）。
- **執行方式**：可以先用 `npm run dev` 或 `npm run build && npm run preview` 起本機伺服器，Playwright 連到本機網址跑（不用連正式站，正式站的登入相關功能本來就測不到）。
- **這次驗證的目的**：不是要建立一套長期維護的 E2E 測試框架（那是更大的工程決策，需要另外討論），而是讓你這次收工前，能自己先跑一輪基本的畫面/互動檢查，減少負責人手動測試才發現問題的往返次數。跑完把腳本留在專案裡即可（例如 `exam-vocab-batcher/e2e/` 或 `tests/` 目錄，你決定放哪裡），不用刻意刪除，但也不用為了它額外寫文件或整合進 CI（CI 整合是之後如果要做才討論，這次不做）。
- **驗證結果要寫進收工報告**：哪些項目測了、結果如何、截圖存在哪裡。

## 邊界（本切片不做）
- 不做完整的 CI/CD 整合 Playwright（例如 GitHub Actions 自動跑 E2E）——這次只是執行層自己收工前的驗證工具，不是要建立正式測試管線。
- 不拿掉頻率/詞性/搜尋篩選功能，只調整視覺優先順序。
- 不動考試出題邏輯、登入邏輯、Firestore 規則、路由選型、PWA 設定。
- 不用 Playwright 測試任何需要真實 Google 帳號登入才能驗證的流程（例如登入後的成績寫入）——這些還是要負責人在真機上測。
