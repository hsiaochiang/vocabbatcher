## 任務一：批次頁面收斂

**檔案：** `src/pages/BatchHubPage.tsx`（第 42~80 行 `features` 陣列）、`src/pages/ExamSetupPage.tsx`

**背景（負責人已拍板，2026-08-03）：**
- 「錄音播放」格（對應原始需求 `REQUIREMENTS.md` R4，批次 TTS 循環播放）→ **正式移除**，不會做。翻牌卡點擊發音＋考試聽力題已滿足核心聽力需求。
- 「練習測驗」「學習統計」→ **接回現有全域功能**，不重做邏輯，只是從批次頁面多一個入口，並且練習測驗要帶入本批次的頁碼範圍當預設值（比操作起來像是「針對這批次出題」，即使背後其實是全域考試引擎在跑）。

**做法：**
1. `BatchHubPage.tsx` 的 `features` 陣列：
   - 移除「錄音播放」那個物件（第 53~61 行）。
   - 「練習測驗」（第 62~70 行）：`available: true`，`onClick` 導向 `/exam`（**注意路由是 `/exam`，不是 `/exam/setup`**，見 `src/App.tsx` 第 22 行），並帶入本批次單字的頁碼範圍當預設值（見下方第 2 點的 `ExamSetupPage` 改動）。
   - 「學習統計」（第 71~79 行）：`available: true`，`onClick` 導向 `/stats`（`src/App.tsx` 第 26 行的既有路由，`WordStatsPage.tsx` 不用改）。
   - 拿掉「錄音播放」格後，畫面會剩三格（翻牌學習／練習測驗／學習統計），`grid grid-cols-2` 版面會自然剩三格排列，檢查一下畫面排版看起來合理（例如最後一格要不要跨欄置中，你自行判斷即可，不強制）。
2. `ExamSetupPage.tsx` 目前完全靠自己的 `useState` 決定頁數範圍（第 15~24 行），不會讀 `location.state`。這裡要讓它能接受從 `BatchHubPage` 帶過去的預設頁碼範圍：
   - 用 `useLocation()` 讀 `location.state`（型別可以定義成 `{ initialMinPage?: number; initialMaxPage?: number }`），有帶值就用它初始化 `pageRange` 的 `useState`（例如 `useState(() => initialMinPage && initialMaxPage ? { minPage: initialMinPage, maxPage: initialMaxPage } : null)`），沒帶值（例如從首頁「開始考試」直接進來，不是從批次頁進來）維持原本行為（`null`，用全書範圍）。
   - `BatchHubPage.tsx` 用批次目前的 `batch.words` 算出這批字的頁碼範圍當作 `initialMinPage`/`initialMaxPage`（可以重用 `getPageRange()`，注意這個函式吃的是 `VocabEntry[]`，`batch.words` 型別要對得上，或就地寫個 min/max 計算也可以，不用勉強重用如果型別對不上）。
3. `docs/planning/REQUIREMENTS.md` 同步調整：
   - R4（批次錄音播放）→ 標記為正式移除（例如在該條後面加註「⚠️ 2026-08-03：負責人拍板不做，見 DECISIONS.md」，不用整段刪除，保留歷史脈絡）。
   - R7（批次歷史與統計）→ 已在 UIUX 系列完成歷史批次列表/續作（`HomePage.tsx` 的「繼續上次」卡片與歷史批次列表），統計部分已由 R11 承接；這裡加註「已透過既有功能滿足，M4 不需要額外開發」。
4. 在 `docs/planning/DECISIONS.md` 記一筆（格式比照 `AGENTS.md` 的 DECISIONS.md 格式），內容比照 `STAGE_4_PLAN.md` 已經寫好的措辭：「2026-08-03 負責人拍板：不做批次 TTS 循環播放格，翻牌卡點擊發音＋考試聽力題已滿足核心聽力需求」，並註明影響 `REQUIREMENTS.md` R4、R7。

## 任務二：邊界情況與效能

**背景：**
- 「0 字批次阻止建立」「空白搜尋結果的空狀態畫面」這兩項在 `BatchBuilderPage.tsx` 其實已經做了（第 263 行 `disabled={selected.size === 0}`、第 249~256 行 `filtered.length === 0` 的「沒有符合條件的單字」空狀態）——**這兩項不用重做，你去看一下確認邏輯還在、沒有被後續改動破壞就好，不用改程式碼**。
- 真正還缺的是「重複批次提示」跟「1231 筆單字捲動效能」這兩項，是本任務的重點。

**做法：**
1. **重複批次提示**：`src/pages/BatchBuilderPage.tsx` 的 `handleCreate()`（第 113~118 行）跟 `handleCreatePageBatch()`（第 120~127 行）目前都是直接建立新批次，不檢查有沒有重複。在建立前檢查 `batches`（從 `useApp()` 拿到的既有批次陣列）裡有沒有「單字組成完全相同」的批次（比較 `words` 陣列裡每個 `word.word` 組成的集合是否相等，不用比較順序）：
   - 如果有重複，跳出確認提示（可以用 `window.confirm`，或比照 `BatchHubPage.tsx` 刪除確認的自訂彈窗風格寫一個小 modal，你選實作量小的），內容類似「已經有一個內容相同的批次「XXX」，仍要建立新的嗎？」，使用者按確定才繼續建立，取消就不建立。
   - 這個檢查是提示，不是強制阻擋——使用者確認後還是可以建立重複批次（例如真的想要兩份獨立進度）。
2. **1231 筆單字捲動效能實測**：
   - `BatchBuilderPage.tsx` 目前不篩選時 `filtered` 會是全部 1231 筆，`main` 區塊（第 239~257 行）直接 `.map()` 全部渲染成 `WordCard`，沒有虛擬化。用 Chrome DevTools Performance 面板或肉眼在中階裝置／模擬慢速 CPU 實測捲動整份清單的流暢度。
   - **如果實測有明顯卡頓**（掉幀、捲動不跟手），加虛擬化——優先考慮用專案已有的相依套件（先檢查 `package.json` 有沒有現成的虛擬清單套件，例如 `react-window`／`@tanstack/react-virtual`，沒有的話挑一個輕量、社群成熟的加進去）。虛擬化實作只需要涵蓋 `BatchBuilderPage.tsx` 這個清單，不用做成共用元件。
   - **如果實測沒有明顯卡頓**（例如現代裝置 + Tailwind 的 `WordCard` 夠輕量，捲動順暢），不用加虛擬化，把實測方式與結果寫進收工報告即可，不要為了「應該要有」而做不必要的工程。

## 任務三：UX 查漏補缺與上線收尾

1. **UX 巡查（快篩，不是重新設計）**：對照 `AGENTS.md` 五階段關卡裡提到的檢核重點，快速過一輪主要頁面（首頁、批次建立器、批次 Hub、翻牌卡、考試設定/作答/結果、單字統計、成績歷史）：
   - Touch target ≥ 44dp：抽查按鈕、輸入框、可點擊卡片的最小可點擊高度（Tailwind 常見寫法是 `min-h-[44px]` 或用 `py-*` 組合湊出足夠高度）。UIUX1~3 已經處理過大部分，這裡是抽查有沒有漏網（例如本次新增的拼字輸入框、送出按鈕、任務一新增的重複批次確認彈窗按鈕）。
   - 每頁一個主 CTA：檢查有沒有頁面同時擺出多個「同等重要」的主要按鈕互相搶注意力，尤其是任務一改版後的 `BatchHubPage`（三格功能格＋刪除按鈕，確認視覺上格子彼此平等、不會有「哪個才是真正該點的」混淆）。
   - 有問題就直接小幅修正（間距、`min-h`），不用大改版面；沒問題就在報告裡記錄「已巡查，無需調整」。
2. **無 ANR／白屏／閃退巡查**：用瀏覽器手動走過一輪（或延續專案既有的 Playwright 習慣寫一組簡單的 smoke 腳本，跑得動就跑，不強制）主要頁面之間的導覽路徑（首頁 → 批次建立器 → 建立批次 → 批次 Hub → 翻牌 → 返回 → 練習測驗 → 作答 → 結果 → 返回首頁 → 單字統計 → 成績歷史），確認每個導頁都正常渲染、沒有出現空白畫面或 JS 錯誤（可以開瀏覽器 console 確認沒有紅字錯誤）。
3. **Smoke test 清單**：把上一點走過的路徑整理成一份簡短的清單，附在收工報告裡（例如「首頁載入 ✓／建立批次 ✓／翻牌學習 ✓／練習測驗（含拼字題）✓／學習統計 ✓／成績歷史 ✓」），不用另建獨立檔案，寫進報告即可。
4. **README.md 使用說明補完**：專案根目錄的 `README.md` 目前內容嚴重過時（還寫著 React Native + Expo、TTS 批次播放，跟實際的 React + Vite PWA、Firebase 登入、四題型考試、成績統計完全對不上）。重寫這份檔案，讓「一個沒碰過這專案的人能看懂怎麼跑起來」，至少包含：
   - 專案是什麼（一句話目標，可參考 `docs/planning/PROGRESS.md` 開頭的「一句話目標」）。
   - 實際技術棧（React + Vite PWA、Firebase Auth + Firestore、部署方式 `.\deploy.ps1`）。
   - 核心功能流程（勾選單字建批次 → 翻牌學習 → 四題型練習「含新增的拼字填空」→ 成績/統計 → 錯題複習）。
   - 開發環境需求（Node.js 版本、`npm install`、`npm run dev`、`npm run build`、`npm run lint` 等指令）。
   - 專案文件地圖：指向 `AGENTS.md`（協作規範）、`docs/planning/`（規劃文件）、`docs/handoff/`（切片交接文件）。
   - 不用寫得像完整的架構文件（那是 `DEVELOPER_LOG.md` 的責任），保持精簡、讓人能跑起來就好。

5. `npm run lint`、`npm run build` 要過。

## 邊界（本切片不做）
- 不改考試出題邏輯本身（`generateExam`／`buildQuestion`／`isSpellingCorrect`）、不改 Firestore 安全規則、不改登入邏輯。
- 不動 `src/App.tsx` 的 `BrowserRouter`（絕對不要改回 `HashRouter`，S3e 花了一整輪診斷才修好的登入根因）、不動 `vite.config.ts` 的 Workbox `navigateFallbackDenylist`（S3f 修好的登入攔截問題）。
- 任務一「練習測驗」串接時，**不修改** `src/services/exam.ts` 既有的頁碼範圍出題邏輯，只是從 `BatchHubPage` 帶預設參數過去；考試成績仍記在使用者帳號下，不綁定 batch id，維持「全域考試」與「批次」是兩個獨立資料流。
- 任務二若判斷需要加虛擬化套件，只處理 `BatchBuilderPage.tsx` 這一個清單，不用把其他頁面（例如翻牌卡列表）也一併虛擬化，除非你發現那些頁面也有一樣的效能問題（目前沒有跡象顯示有）。
- 任務三的 README 改寫只動根目錄 `README.md`，不用動 `exam-vocab-batcher/README.md`（那份是前端子專案自己的，若內容也過時，可以在報告裡提一句給規劃層知道，但不強制這片一起改）。

## 驗收（負責人操作）
1. 進任一批次頁，確認只剩三格（翻牌學習／練習測驗／學習統計），沒有「即將推出」的字樣。
2. 點「練習測驗」，確認直接帶你去考試設定頁，且頁碼範圍已經自動幫你選好這批次的範圍（不是全書範圍）。
3. 點「學習統計」，確認會看到單字統計頁。
4. 用同一批單字（例如同一頁課本）建立第二次批次，確認會跳出「已有相同批次」之類的提示，不是悄悄就建立了。
5. 進階搜尋打一個查不到的關鍵字，確認畫面有清楚的「沒有符合條件的單字」提示而不是空白；不選任何字直接想建立批次會被擋下（按鈕是灰色不能按的）。
6. 捲動整份 1231 字清單（批次建立器不選任何篩選時），感受一下順不順（若這片有加虛擬化，體感應該會更順；若沒加，代表實測本來就順暢）。
7. 用手機瀏覽器把每個主要頁面都點過一輪（首頁、批次建立器、批次 Hub、翻牌、考試設定/作答/結果、單字統計、成績歷史），確認沒有整頁空白或整個 App 沒反應的狀況。
8. 讀一下 `README.md`，確認一個沒碰過這專案的人看得懂這是什麼、怎麼跑起來。
9. iPhone Safari、Android Chrome 各測一次任務一（練習測驗帶預設頁碼範圍）跟任務二（重複批次提示）的流程。
10. `npm run lint`、`npm run build` 通過。
