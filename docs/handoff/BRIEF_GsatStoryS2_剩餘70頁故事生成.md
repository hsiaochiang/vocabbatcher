# BRIEF_GsatStoryS2_剩餘70頁故事生成.md — 學測 Minecraft 故事模式切片2：剩餘75頁內容生成

> 交接合約：規劃層 → 執行層，2026-08-13。
> 背景：負責人想在學生選定一頁學測單字開始背誦時，額外提供「用這一頁全部單字寫成一個 Minecraft 主題故事」的例句功能，用敘事/脈絡化學習法增加記憶效果。規劃層已在對話中直接手動生成學測第 16~20 頁共 5 頁試行內容，負責人審閱通過（含中文翻譯與可點擊發音的資料結構設計）。這片要把剩下 75 頁（第 1~15、21~80 頁）依同樣品質標準生成完成。**這片純粹是內容生成，不碰 App 程式碼**（App 端串接是之後的切片3，另外開 BRIEF）。

## 開場指令（執行層開工先做）
1. 讀 `docs/planning/PROGRESS.md` 恢復脈絡。
2. 讀規劃層已產出的試行成果 `output/story/gsat/stories_pilot_16_20.json`（第 16~20 頁，已通過負責人審閱，是這片的格式與品質標準範本，**不要重新生成或修改這 5 頁**）。
3. 工作目錄為專案根目錄。

## 目標（一句話）
> 用 Minecraft 主題故事，把學測單字庫剩下 75 個頁碼（第 1~15、21~80 頁，共 1231-101=1130 個單字）都各自寫成一篇自然、適合國小剛升國一學生閱讀的故事，每個單字都要自然出現在對應頁碼的故事裡，最終合併成一份 `stories.gsat.json` 供之後的 App 切片使用。

## 現況（可直接重用）

- 單字資料來源：`exam-vocab-batcher/public/data/vocab.gsat.cleaned.json`。每筆 `VocabEntry` 含 `word`、`pos`、`zh_definition`、`source_page`（陣列，一個字可能出現在多個頁碼——生成某頁故事時，只看 `source_page` 陣列裡包含該頁碼的字，一個字若同時屬於這頁與其他頁，正常收錄即可，不用特別排除）。
- 頁碼範圍：學測資料共 80 頁（第 1~80 頁，中間沒有缺頁——2026-08-13 當天規劃層才剛修過這份資料的頁碼欄位錯誤，見 `docs/planning/DECISIONS.md` 2026-08-13「修復學測資料來源檔頁碼欄位」條目，**現在的頁碼欄位是正確的，不要懷疑或去改它**）。第 16~20 頁已經做完，這片只需要 1~15、21~80 共 75 頁。
- 資料結構範本（schemaVersion 2，直接照 `output/story/gsat/stories_pilot_16_20.json` 的格式）：
  ```jsonc
  {
    "schemaVersion": 2,
    "stories": [
      {
        "id": "gsat-p<頁碼>-minecraft",
        "source": "gsat",
        "page": <頁碼 number>,
        "theme": "minecraft",
        "wordList": ["這一頁全部單字，原形，跟 vocab.gsat.cleaned.json 的 word 欄位完全一致"],
        "generatedAt": "<ISO時間字串>",
        "sentences": [
          {
            "index": 0,
            "text": "英文句子，包含這句對應的目標單字",
            "zh": "台灣慣用語中文翻譯，目標單字用全形括號標註英文原文，例如「測試自己的認知能力（cognitive）」",
            "targetWords": ["這句對應的目標單字，通常1個，最多不超過3個"]
          }
        ]
      }
    ]
  }
  ```
- QA 腳本範本：`output/story/gsat/qa_check.py`——規劃層已經寫好，直接沿用或視需要擴充，確認兩件事：① 每頁 `wordList` 的每個字都能在該頁全部句子的英文 `text` 拼接後的文字裡找到（不分大小寫、允許字尾變化如 -s/-ed/-ing，只要是包含關係即可）；② 每個 `targetWords` 都能在對應句子的 `zh` 字串裡，用全形或半形括號包住的形式找到（這是之後 App 端要用括號比對做「點英文字發音」功能的資料基礎，**這個格式規則不能省略**）。

## 任務

1. **逐頁生成故事**（第 1~15、21~80 頁，共 75 篇）：
   - 每頁固定 Minecraft 主題，語氣、句子長度、難度比照第16~20頁試行版本（`output/story/gsat/stories_pilot_16_20.json`）——目標讀者是剛升國一的學生，故事本身連接的敘述用詞要簡單自然，只有目標單字本身可以是較難的詞。
   - 每句盡量只放 1 個目標單字（最多3個），不要為了塞字硬湊出不通順的句子。**規劃層在試行時發現 `derive` 一開始寫成 "she could derive a clue"（derive 較常見的搭配是 derive information/meaning，不是 derive a clue），被負責人抓出來當作真實案例——這是這片最主要的品質風險，每個單字用完寫完之後最好自己讀一遍，確認搭配自然，不是「查到字義硬套進句子」。**
   - 若某個單字真的很難自然融入（學測單字比會考抽象，例如 subsequent、compassionate、democratic 這類詞），寧可用基本形式也不要跳過不寫；不能為了通順而漏掉任何一個目標單字。
   - 每句都要有對應的中文翻譯 `zh`，用台灣慣用語（不是中國大陸用語），目標單字用全形括號標註英文原文，格式比照試行版本。
   - `wordList` 欄位裡的字要跟 `vocab.gsat.cleaned.json` 該頁的 `word` 欄位完全一致（同樣的拼法、同樣的大小寫），這是後續 QA 比對與 App 端顯示要用的基準值。

2. **QA 驗證**：
   - 用（或擴充）`output/story/gsat/qa_check.py` 對這 75 頁跑過，兩項檢查（英文單字覆蓋、中文括號標註）都要全過。
   - 若有頁面真的無法讓某幾個字自然通過檢查（例如自動比對抓不到，但人工看內容其實有涵蓋，只是字尾變化型態沒被腳本認出來），可以微調 QA 腳本的比對規則使其更寬鬆合理，但**不能把没真的用到的字，改成腳本強行判定過關**——如果真的漏了某個字，要回頭補寫句子，不能篡改 QA 邏輯繞過去。
   - 產出一份 QA 報告（可以是終端機輸出存成文字檔、或仿照 `src/pdf_parser/qa.py` 產出 JSON 報告，你自行決定格式，但要讓規劃層事後能一眼看出「75 頁裡幾頁全過、有沒有頁面沒過」），存到 `output/story/gsat/qa_report_s2.json`（或你覺得更合理的檔名，在報告裡說明）。

3. **合併輸出**：
   - 把試行的 5 頁（`output/story/gsat/stories_pilot_16_20.json`）與這片新生成的 75 頁，合併成一份完整的 `stories.gsat.json`（共 80 頁），存到 `output/story/gsat/stories.gsat.json`。
   - **先不要複製進 `exam-vocab-batcher/public/data/`**——App 端串接是切片3的事，這片只負責把資料準備好放在 `output/story/gsat/`，不要提前動 `public/data/` 目錄，避免切片3還沒做資料結構就已經半路出現在正式資料夾裡造成混淆。
   - 若 QA 有頁面沒過，**不要把沒過的頁面塞進最終的 `stories.gsat.json`**（partial-ship-and-backfill 原則——寧可先交 79 頁完整的，也不要交 80 頁裡混一頁品質有問題的），在報告裡列清楚哪幾頁沒過、原因是什麼，讓規劃層跟負責人決定後續怎麼補。

## 邊界（本切片不做）

- **不碰 `exam-vocab-batcher/src/` 底下任何檔案**（`.tsx`／`.ts` 都不動）——這片純粹是資料生成，App 端的 `Batch.sourcePage` 欄位、`BatchHubPage` 故事分頁、`StoryPage` 元件，都是切片3的工作，現在還沒有 BRIEF。
- **不改 `exam-vocab-batcher/public/data/vocab.gsat.cleaned.json`**——這份單字資料本身（含頁碼欄位）今天已經修過、負責人已確認正常，這片只讀取它、不寫入它。
- **不改第 16~20 頁的內容**——那 5 頁是規劃層手動生成、負責人已經審閱通過的，這片只需要「補完剩下 75 頁」，不要因為想統一風格而重寫已通過的部分。
- **不用申請或呼叫任何外部 AI API（Gemini 等）**——這片的故事內容由你（Codex，執行層本身的語言能力）直接生成，不需要另外的模型或金鑰，這是負責人明確要求的做法，跟這個專案其他資料 pipeline（呼叫外部 OCR/AI 服務）不一樣，不要自己加裝依賴去呼叫外部 LLM。
- **不做多主題**——固定 Minecraft 一種主題，不要自己發揮做成其他主題或讓故事風格分裂不一致。
- **不用做「整段自動連續播放」或任何 App 互動邏輯**——那些是 UI 層的事，這片只產資料。
