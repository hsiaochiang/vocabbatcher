# BRIEF_UIUX3_頁碼修正與單頁建立批次.md — 資料修正 + 批次建立流程簡化

> 交接合約：規劃層 → 執行層，2026-08-03。
> 背景：`BRIEF_UIUX2` 上線後，負責人發現兩個問題：
> (1) App 裡的「頁次」其實是 PDF 檔案內部的頁面編號，跟課本印刷頁碼對不上，差了固定 2（例如 App 顯示的
> 頁次 9，實際對應課本頁碼 7）；規劃層查過 `src/pdf_parser/` 的程式碼與資料，證實整本書從頭到尾都固定
> 差 2（PDF 內容第 3 頁 = 課本印刷頁碼第 1 頁），已跟負責人確認採用「固定偏移量快修」，不重新解析 PDF。
> (2) 建立批次目前的操作太多步驟（設定頁次範圍→篩選→全選→按建立批次），負責人希望改成「一個按鈕一個
> 頁次，按下去就等於完成建立批次」，因為使用者實際使用情境是照課本頁碼一頁一頁準備，不是抓一個範圍。
> 規劃層已確認：全書每頁單字數落在 18~21 個之間，都在批次上限 25 字以內，「一頁 = 一個批次」在資料面上
> 完全可行，不會遇到超過 25 字要處理的情況。

## 開場指令（執行層開工先做）
1. 讀 `PROGRESS.md` 恢復脈絡。
2. 讀 `REPORT_UIUX2_頁次篩選與自動化驗證.md` 了解上一片剛做的頁次篩選（本片會取代它的部分邏輯）。
3. 工作目錄橫跨專案根目錄（Python pipeline）與 `exam-vocab-batcher/`（前端）。

## 目標（一句話）
> 修正頁碼資料的固定 2 頁偏移，並把批次建立器改成「點一個頁碼按鈕＝立刻建好那一頁的批次」，貼合使用者照課本頁碼準備的實際習慣。

## 任務

### 1. 修正頁碼偏移（資料 + pipeline 兩處都要修，缺一不可）

**(a) 修正目前部署中使用的資料檔：**
- `exam-vocab-batcher/public/data/vocab.cleaned.json`：每筆資料的 `source_page` 陣列，每個數字都減 2。
- `output/vocab.cleaned.json`：同樣邏輯，每個 `source_page` 數字減 2（維持這份 pipeline 輸出跟前端實際使用的資料一致，避免以後又對不起來）。
- 修正後跑一次資料檢查：確認沒有任何 `source_page` 減完是 0 或負數（規劃層已初步確認全書資料原始最小值是 3，減 2 後最小會是 1，理論上安全，但你動手改之前還是要實際跑一次驗證，不要只信規劃層的預先檢查）。

**(b) 修正 pipeline 原始碼，避免以後重新解析 PDF 又跑出一樣的偏移：**
- 檢查 `src/pdf_parser/extractor.py`（`page_num = page.page_number`，直接用 PDF 內部頁碼）、`src/pdf_parser/parser.py`（`entry["source_page"] = page.page_number`）——先確認目前 `output/vocab.cleaned.json` 實際是哪一條 pipeline（`top2025.py` 規則 or `top2025_md.py` 規則）產生的，只修正實際有在用的那條路徑，不要兩條都亂改。
- 在確認的那個檔案裡，把計算 `source_page` 的地方減去一個明確命名的常數（例如 `PRINTED_PAGE_OFFSET = 2`），並寫清楚註解：這個偏移量是 `top2025.pdf` 這份文件特有的（封面/目錄佔了 PDF 前 2 頁、正文印刷頁碼從 PDF 第 3 頁開始），如果以後換一份新的來源文件，這個常數需要重新確認，不能假設永遠是 2。
- 若你判斷這樣的修改風險太高、或牽動的 pipeline 程式碼超出這次能安全驗證的範圍，可以退而求其次：只做任務 (a) 的資料檔修正，把 pipeline 原始碼修正記錄成 `DECISIONS.md` 的「待辦」讓規劃層知道還沒做，不要為了硬修 pipeline 而冒然改壞既有的 Python 測試（`tests/test_parser.py`）。跑一下 `pytest`（如果環境裡有裝）確認沒改壞既有測試。

**(c) 這個修正的影響範圍要記錄清楚：**
- S3「考試引擎」的「選頁數範圍出題」功能，從上線以來頁碼範圍其實都是跟印刷頁碼差 2 的——不是功能邏輯錯，是頁碼「數字標示」跟使用者認知的課本頁碼對不上。修正後，同一個功能的頁碼範圍會自動對齊課本印刷頁碼（`ExamSetupPage.tsx` 用 `getPageRange(allWords)` 動態算全書範圍，資料改了之後不用碰這段程式碼）。
- 這條務必記進 `DECISIONS.md`，講清楚：背景（使用者發現的落差）、改了什麼（資料減 2、pipeline 常數化）、影響哪些既有功能（S3 考試引擎的頁數範圍、這次 UIUX2 剛做的頁次篩選）。

### 2. 批次建立器改成「一頁一按鈕，按下即建立批次」

- **檔案：** `src/pages/BatchBuilderPage.tsx`（UIUX2 剛加的頁次範圍輸入框，這次要替換成新的互動方式）
- **修法：**
  - 把原本的「頁次範圍（最小頁～最大頁輸入框）」，改成一整排（或格狀排列）的**頁碼按鈕**，每個按鈕對應全書裡實際有單字資料的一個頁碼（用修正後的 `source_page` 算出全書有出現過的頁碼清單，由小到大排列）。
  - 按鈕文字直接顯示頁碼數字（例如「1」「2」「3」...），可以加小字標示這頁有幾個字（例如「1｜19 字」），方便使用者判斷。
  - **點下某個頁碼按鈕，直接用該頁的全部單字建立一個新批次**，不需要使用者再手動勾選、再按一次「建立批次」——等同於原本「選頁次範圍→全選篩選結果→建立批次」三個步驟合併成一個點擊。建立完成後導向新批次的 `BatchHubPage`（跟現有 `handleCreate` 導頁邏輯一致）。
  - 批次名稱建議自動帶入頁碼資訊（例如「批次 #N（第 X 頁）」），方便使用者在首頁「歷史批次」列表分辨這是哪一頁做的批次；`createBatch()` 目前簽名只接受 `words: VocabEntry[]`，如果要帶自訂名稱，你評估是否要擴充 `AppContext.createBatch()` 支援可選的名稱參數，或建立後用 `updateBatch()` 補改名稱，兩種做法都可以，挑實作量小的。
  - **原本的頻率／詞性／搜尋篩選（進階篩選）保留**，放在頁碼按鈕下方，供使用者想要「手動勾選特定單字」而不是整頁全收的情境使用——這種情境下維持原本「勾選→按建立批次」的流程不變（既有的 `selected`/`handleCreate` 邏輯不用大改，只是不再是唯一入口）。也就是說，畫面上會同時存在「快速：點頁碼建立整頁批次」與「進階：手動勾選＋篩選」兩種路徑，快速路徑放最上面、最主要的位置。

### 3. 用 Playwright 驗證這次的修正（延續 UIUX2 建立的自動化驗證習慣）
- 更新或新增 `e2e/` 底下的測試，至少涵蓋：
  - 頁碼按鈕清單有正確顯示（跟修正後的資料筆數/頁碼數字對得上）。
  - 點一個頁碼按鈕後，確實直接建立了批次並導頁到該批次的頁面，批次字數等於該頁的單字數。
  - 進階篩選（頻率/詞性/搜尋）流程沒有因為這次改版而壞掉。
- 把驗證結果（含截圖）寫進收工報告，比照 `BRIEF_UIUX2` 的做法。

## 邊界（本切片不做）
- 不重新解析 PDF、不重建整個 `vocab.raw.json`／`vocab.qa_report.json`（只動 `vocab.cleaned.json` 跟 pipeline 裡計算 `source_page` 的那一小段）。
- 不改考試出題邏輯、登入邏輯、Firestore 規則、路由選型、PWA 設定。
- 不用因為批次建立器改版而更動 `ExamSetupPage`／考試引擎的頁數範圍邏輯，那邊本來就是動態算全書範圍，資料修正後會自動對齊，不用碰程式碼。

## 驗收（負責人操作）
1. 部署後開「建立新批次」，畫面應該是一排頁碼按鈕（不是原本的最小頁/最大頁輸入框）。
2. 拿你手上的課本，隨便翻到某一頁，點 App 裡對應的頁碼按鈕，確認出現的單字**真的是課本那一頁上的字**（這是這次修正的核心驗收點）。
3. 點下去之後，確認直接進到新批次的頁面，不需要再多按一次「建立批次」。
4. 往下滑，確認「進階篩選」（頻率/詞性/搜尋）還在，用它手動勾選幾個字、建立批次，確認這條路徑也還能正常運作。
5. 進「開始考試」，設定頁數範圍時，確認全書範圍的數字（左右邊界）現在對得上課本實際頁碼，不再差 2。
6. iPhone Safari、Android Chrome 各測一次「點頁碼建立批次」的流程。
7. `npm run lint`、`npm run build` 通過；Python 那邊如果有動 pipeline 程式碼，確認沒有改壞既有測試。
